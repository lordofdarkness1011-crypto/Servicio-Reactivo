2. Conceptos que ambos deben aplicar por igual
Para que el informe sea comparable, los dos modelos deben documentarse con la misma estructura. Antes de repartir tareas conviene alinear el vocabulario.
2.1. TDD: Red–Green–Refactor
Cada funcionalidad probada debe evidenciar el ciclo de tres fases. En el informe se muestra con una captura o fragmento por fase:
Red (rojo): se escribe primero la prueba, que falla porque la funcionalidad aún no existe o no cumple. Se adjunta la evidencia del test en rojo.
Green (verde): se implementa el mínimo código necesario para que la prueba pase. Evidencia del test en verde.
Refactor: se mejora el código (nombres, duplicación, estructura) manteniendo las pruebas en verde. Se explica qué se refactorizó y por qué.
2.2. Patrón AAA (Arrange–Act–Assert)
Toda prueba debe estar estructurada visiblemente en tres bloques, idealmente separados con comentarios:
Arrange: preparar datos, mocks, cliente HTTP, estado inicial.
Act: ejecutar la acción bajo prueba (la llamada al endpoint o al servicio).
Assert: verificar el resultado esperado (status, cuerpo, número de elementos, tiempo, etc.).
Ejemplo mínimo del patrón AAA (a incluir en cada modelo)
// Arrange
var request = new ProductoDTO("Teclado", 25.0);
// Act
var response = webTestClient.post().uri("/productos").bodyValue(request).exchange();
// Assert
response.expectStatus().isCreated();
2.3. Definiciones de la parte de automatización
Concepto
Qué se espera evidenciar
Integración Continua (CI)
Un pipeline que, ante cada push/PR, compila y ejecuta las pruebas automáticamente. Evidencia: archivo de workflow + ejecución en verde.
Pruebas de integración
Pruebas que levantan el contexto de Spring y validan el endpoint contra una base de datos real (o Testcontainers), no solo unitarias.
Despliegue Continuo (CD)
Que al pasar CI, la aplicación se empaquete y despliegue automáticamente (imagen Docker, Render/Railway, etc.). Evidencia: pipeline de deploy + URL o contenedor corriendo.
